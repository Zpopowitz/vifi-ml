# Security Hardening — SP7 partial

What the live stack looks like under the production security posture, why
each control matters, and the exact commands to flip from SP1 bench mode
(`VIFI_AUTH_MODE=none`) to production mode.

Companion to `docs/LIVE_STACK.md`. The full SP7 sub-project (TLS via the
compose `caddy` profile, secret rotation cadence, audit-chain
verification CI job) lands later; this doc covers what's enabled by
`tools/enable_security_mode.sh` today.

---

## Threat model

The SP1 bench was scoped explicitly to a trusted single-host LAN (Pi
loopback for Redis, dashboard on `0.0.0.0:8000` from the home WiFi). SP7
flips the assumption: any client of the stack must prove possession of a
secret, the bus is no longer reachable without one, and the audit log is
tamper-evident.

Concrete things SP7-partial defends against:

| Threat | Control |
|---|---|
| Random LAN client hits `/predict` / `/api/v1/stream` | API-key gate (`VIFI_AUTH_MODE=api_key` + `X-Api-Key` header) |
| Anyone with shell access to the Pi reads patient ids | Pseudonymisation salt in audit log (`VIFI_PSEUDO_SALT`) |
| Compromised audit log doesn't show tampering | HMAC chain key (`VIFI_AUDIT_CHAIN_KEY`) |
| At-rest audit log is grep-able for plaintext PHI | Fernet at-rest encryption (`VIFI_AUDIT_ENCRYPTION_KEY`) |
| Open Redis on the host exposes the bus | Redis `requirepass` + password-embedded `VIFI_BUS_URL` |

Things SP7-partial does NOT yet defend against (full SP7 will):

- Man-in-the-middle on the local LAN (no TLS yet — the dashboard is
  served on HTTP). Enable the compose `caddy` profile for TLS in full SP7.
- Lost / leaked secrets without forced rotation cadence (manual
  rotation is supported now; SP7 adds enforcement).
- Authenticated-but-malicious internal client (no per-key scopes
  enforced in this partial flip; key metadata + scope enforcement is
  already in the codebase but the simple `VIFI_API_KEYS` env mode
  grants `"*"` to every key — full SP7 moves to `VIFI_API_KEYS_FILE`).

## The five secrets

All are generated by `tools/setup_keys.sh` and live in the local `.env`
file (which is `.gitignored` and lands at chmod 600). The hardening
script reads them and writes them to `/etc/vifi/live.env` on the Pi.

| Env var | Purpose | Rotation impact |
|---|---|---|
| `VIFI_API_KEYS` | Comma-separated allowed API keys. Implicit `"*"` scope per key. | Old key invalid immediately; all callers must update. |
| `VIFI_PSEUDO_SALT` | HMAC salt for pseudonymising patient ids in the audit log. | Old audit records use a different namespace — keep both salts during a migration window. |
| `VIFI_AUDIT_ENCRYPTION_KEY` | Fernet key for at-rest audit-log encryption. | Old audit files un-decryptable without the old key — archive the old key with the old files. |
| `VIFI_AUDIT_CHAIN_KEY` | HMAC key for the tamper-evident audit chain. | New chain starts fresh; older chain still verifiable against the old key. |
| `VIFI_REDIS_PASSWORD` | Redis `requirepass`. Embedded into `VIFI_BUS_URL` so every client picks it up via `EnvironmentFile`. | Bus disconnects briefly; every service has to be restarted with the new password (the helper script does this for you). |

## Enable security mode (one command)

```bash
# From WSL, with the SP1 stack already deployed (./tools/setup_live_stack.sh done):
./tools/enable_security_mode.sh
```

What it does (idempotent — re-running with the same `.env` is a no-op
beyond a restart):

1. Generates `.env` locally via `tools/setup_keys.sh` if missing
   (otherwise leaves it). Pass `--rotate-all` to force fresh secrets.
2. SSHes to the Pi, writes the SP7 env vars into `/etc/vifi/live.env`
   (replacing any prior security lines).
3. Adds a managed `requirepass` block to `/etc/redis/redis.conf`,
   restarts `redis-server`.
4. Rebuilds `VIFI_BUS_URL` to include the password.
5. Restarts the four (or six with radar) vifi services so they pick up
   the new env + new bus URL.
6. Verifies: `curl http://localhost:8000/health` without the API key
   now returns **401**.

Dry-run mode shows what would change without writing:

```bash
./tools/enable_security_mode.sh --dry-run
```

Force a fresh secret set (deprecates ALL prior keys):

```bash
./tools/enable_security_mode.sh --rotate-all
```

## Day-to-day after enabling

Every API call needs the key:

```bash
# From WSL (the API key lives in your local .env's VIFI_API_KEYS):
KEY=$(grep VIFI_API_KEYS .env | cut -d= -f2 | cut -d, -f1)
curl -sS -H "X-Api-Key: $KEY" http://vifi-pi-room1.local:8000/health
```

The dashboard prompts for the key in its login overlay (already shipped
in SP1's dashboard SPA). After entering once, the key is stored in
`localStorage` for the session.

`./tools/capture.sh --live` works unchanged — the orchestrator on the
Pi reads the bus password from `EnvironmentFile`, so it gets it for
free.

## Rotating a single secret (no script-wide disruption)

`tools/setup_keys.sh --rotate <VAR>` is the operator path. Per-secret
guidance:

```bash
# Rotate the API key (others stay):
./tools/setup_keys.sh --rotate VIFI_API_KEYS
./tools/enable_security_mode.sh           # re-push to the Pi + restart

# Rotate the Redis password (more disruptive — bus blips):
./tools/setup_keys.sh --rotate VIFI_REDIS_PASSWORD
./tools/enable_security_mode.sh

# Rotate the audit chain key — start a new chain, keep the old key for
# verifying the previous file:
./tools/setup_keys.sh --rotate VIFI_AUDIT_CHAIN_KEY
./tools/enable_security_mode.sh

# Rotate the at-rest encryption key — archive old key with old log file
# before doing this; otherwise old records are unrecoverable:
cp audit/audit-*.jsonl audit/archive/
./tools/setup_keys.sh --rotate VIFI_AUDIT_ENCRYPTION_KEY
./tools/enable_security_mode.sh
```

Rotation cadence — pick one and stick to it:

- API keys: monthly (or per departing clinician / contractor).
- Pseudonymisation salt: never (changes audit log namespacing).
- Audit encryption key: yearly, archive old files first.
- Audit chain key: with the encryption key (treat them together).
- Redis password: yearly or on suspected compromise.

## Verification — did it actually work

Five checks; run all of them after enabling:

```bash
# 1. /health without the key returns 401.
curl -sS -o /dev/null -w "%{http_code}\n" http://vifi-pi-room1.local:8000/health

# 2. /health WITH the key returns 200.
KEY=$(grep VIFI_API_KEYS .env | cut -d= -f2 | cut -d, -f1)
curl -sS -o /dev/null -w "%{http_code}\n" -H "X-Api-Key: $KEY" http://vifi-pi-room1.local:8000/health

# 3. Redis is password-protected (anonymous ping fails).
ssh pi 'redis-cli -e ping'   # expect (error) NOAUTH ...
ssh pi 'redis-cli -a "$VIFI_REDIS_PASSWORD" ping'   # PONG (after loading env)

# 4. Audit log boot guard fires when chain key is missing.
ssh pi 'sudo systemctl restart vifi-audit && sleep 1 && journalctl -u vifi-audit -n 10 --no-pager | grep -i "chain key"'
# expect: "audit chain key active" — if you see "VIFI_ALLOW_INSECURE_AUDIT" the
# guard was overridden; that should not be on in production.

# 5. A capture still works end-to-end (with the key in environment).
./tools/capture.sh --live --duration 30
```

If any of 1-4 fail, run `./tools/enable_security_mode.sh --dry-run` to
inspect what's diverged.

## What's still missing (full SP7)

- TLS termination via the compose `caddy` profile (the LAN is
  plaintext today even with auth).
- Per-key scopes via `VIFI_API_KEYS_FILE` (the simple env-var mode
  grants every key `"*"`; for separation-of-duties you want
  `read:hr` / `read:identity` / `write:audit` scoped).
- Forced rotation cadence (cron + alerting when a key is N days old).
- Audit-chain verification CI job (does the chain HMAC verify
  end-to-end at every PR).

All of those land in full SP7. The plumbing is in the codebase; this
doc is the bridge from "implemented" to "actually flipped on."
